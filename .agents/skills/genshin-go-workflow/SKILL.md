# Genshin-Go 需求工作流

用中文沟通。遵循项目 `AGENTS.md`，先读 `README.md`，按需检查源码、`GLOSSARY.md` 和相关 ADR。拿已有设计和行为作为讨论依据。

## 阶段交接

- 按下列顺序执行。用户提出需求即开始阶段 1。开始阶段 2 至 5 前，逐项复核上一阶段的完成条件和当前产物，再用一条消息概述成果、验证证据和下一阶段要做的事，询问是否同意开启该阶段。
- 只接受用户在收到自查结果后对所指明下一阶段的明确答复，例如「确认，开始修改 UI/UE」。用户补充需求或要求修改时，先处理这些反馈。用户只认可当前成果、表示稍后继续或提前授权后续多个阶段时，仍继续等待对下一阶段的单独确认。用户可以在同一条答复中认可当前成果并明确同意开启下一阶段。
- 自查发现缺项时，先在当前阶段补齐。等待确认时暂停下一阶段的工作，包括起草、编辑和发布。每次确认仅授权所指明的阶段，仍须完成该阶段内部的核对与确认。
- 根据对话和实际产物恢复进度。需求或已确认产物发生实质变化时，回到最早受影响的阶段，重新自查并逐段取得确认。

## 1. 接收需求

记录用户原始需求、期望结果和已给出的约束。把仍需选择的事项带入需求访谈。

完成条件：能准确复述用户想解决的问题和预期结果，已记录用户给出的范围及约束。自查后询问是否开启阶段 2 的需求访谈。

## 2. 互动确认需求

使用 `grill-with-docs`，按其指引执行 `grilling` 和 `domain-modeling`。优先使用可用的 skill 调用入口。如果当前环境只提供文件读取，从 `C:/Users/tyc/.agents/skills/` 读取并执行 `grill-with-docs/SKILL.md`、`grilling/SKILL.md` 和 `domain-modeling/SKILL.md`。先查清代码和文档可回答的问题，再分轮与用户确认决策。按需更新项目术语表和 ADR。找不到所需 skill 时，说明缺少的路径或能力，保持在本阶段。

完成条件：用户确认了目标、范围、关键流程与验收行为，本次范围内没有阻塞下一阶段的未决问题，需要记录的术语或决策已写入项目文档。自查后询问是否开启阶段 3，并说清准备修改的设计、原型或界面。

## 3. 修改 UI/UE

按已确认范围修改项目现有设计稿、交互原型或实际界面。通过可查看的成果展示关键路径和本次涉及的状态。若改到产品代码，按 `AGENTS.md` 执行相应检查。需求没有界面影响时，也要核对现有界面和用户路径，记录依据，并请用户确认这个结论。

完成条件：按阶段 2 的验收行为检查成果，给出可查看的产物和实际验证结果。如果还有影响验收的缺项，留在本阶段处理；如果用户尚未验收 UI/UE，可以在交接消息里同时请求认可成果和同意开启阶段 4。明确阶段 4 包含向项目 GitHub Issues 发布规格。

## 4. 生成并发布规格

使用 `to-spec`。若无法直接调用，读取并执行 `C:/Users/tyc/.agents/skills/to-spec/SKILL.md`。从已确认的需求和 UI/UE 成果综合规格，先和用户确认测试从哪些可观察的入口验证，再按 `docs/agents/issue-tracker.md` 和 `docs/agents/triage-labels.md` 将规格发布到 `IannTao/genshin-go`。创建前检查重复项。

完成条件：回读 GitHub Issue，核对规格内容与标签，记录 Issue 编号和链接。发布失败时留在本阶段。自查后询问是否开启阶段 5，并说明将以该规格 Issue 为父项拆分和发布任务。

## 5. 拆分并发布任务

使用 `to-tickets`，输入阶段 4 的 GitHub Issue。若无法直接调用，读取并执行 `C:/Users/tyc/.agents/skills/to-tickets/SKILL.md`。提出可独立验证的纵向任务切片、验收标准和阻塞依赖，获得用户对拆分方案的明确批准后再发布。遵循项目任务跟踪约定，按依赖顺序发布并建立父子及阻塞关系。发布中断时，查找并复用已创建的 Issue，再补齐剩余工作。

完成条件：回读任务并核对内容、标签、父子关系与阻塞依赖，向用户交付规格链接、任务链接和依赖关系。只有完成核对后才宣布工作流结束。
